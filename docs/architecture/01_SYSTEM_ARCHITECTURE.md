# System Architecture & Operational Boundary Specification

> **System Classification**: Academic Prototype & Research Demonstration Platform  
> **Canonical Positioning Statement**:  
> *"An evidence-driven academic prototype integrating SIEM-style event ingestion, UEBA, anomaly detection, AI-assisted investigation, attack correlation, MITRE ATT&CK mapping, response simulation, human approval, and continuous learning into one coherent workflow."*

---

## 1. Operational Boundaries and Safety Guardrails

### 1.1 Non-Negotiable Safety Invariants
1. **Simulation-Only Response**: This platform operates entirely in an isolated software-emulated domain. All mitigation actions are strictly simulated within an in-memory graph model (the Digital Twin) and a database state machine.
2. **Absolute Prohibition of Active System Mutation**: The system contains no native bindings, system calls, subprocess executions, network drivers, API integrations, or shell wrappers capable of:
   - Operating system-level process termination or socket destruction
   - Firewall rule alteration (iptables, nftables, Windows Filtering Platform)
   - Active Directory, LDAP, OAuth, or local OS user account disabling
   - Physical or virtual host network isolation or interface downing
   - Storage volume unmounting, encryption, or destructive deletion
   - Real-world network traffic redirection or DNS poisoning
3. **Realistic Claims & Commercial Boundaries**:
   - The platform **does not claim 100% security or invulnerability** to cyber threats.
   - The platform **does not claim to replace commercial enterprise SIEM, EDR, XDR, or SOAR solutions** (e.g., Splunk, Microsoft Sentinel, CrowdStrike Falcon, Palo Alto Cortex XSOAR). It is designed to illustrate automated correlation, human-in-the-loop triage, and deterministic risk reasoning in a research environment.

### 1.2 Mandatory Output Labelling Standards
Every interface, API response, visualization node, and exported artifact must adhere to standard taxonomic labelling to prevent operational ambiguity:

| Label Marker | Semantic Definition | Application Domain |
| :--- | :--- | :--- |
| `SYNTHETIC DATA` | Data generated by synthetic engines or deterministic generators for scenario testing. | Ingested events, synthetic user profiles, demo assets, mock alerts. |
| `POTENTIAL ANOMALY` | Statistical outlier or ML feature deviation with zero guaranteed malice. | Isolation Forest outputs, z-score flags, deviation vectors. |
| `ESTIMATED PREDICTION` | Heuristic or probabilistic estimation of attack progression or impact. | MITRE next-step prediction, blast-radius scope, similar incident matching. |
| `SIMULATED ACTION` | Defensive countermeasure calculated and applied to the Digital Twin model only. | Block IP, Isolate Device, Revoke Token, Restrict Access. |
| `INTERNAL EVALUATION METRIC` | Locally calibrated score computed for research comparison, not an industry standard. | Security Health Score, Detection Confidence, Evidence Quality. |

## 4. Detailed Component & Service Decomposition

### 4.1 Event Ingestion Service
- **Role**: Entry conduit for external and synthetic security logs.
- **Protocols**:
  - `POST /api/v1/events/ingest`: Direct JSON event or batch ingestion.
  - `POST /api/v1/events/upload-csv`: High-throughput CSV file upload with streaming chunk validation.
  - `POST /api/v1/events/upload-json`: Structured JSON batch file upload.
- **Processing Logic**:
  - Schema validation via Pydantic v2.
  - Timestamp normalization to UTC ISO-8601.
  - IP validation (IPv4/IPv6 RFC compliance) and enrichment (private/public classification).
  - Deduplication check via SHA-256 hash of `(timestamp, username, source_ip, destination_ip, event_type, action)`.
  - Batch persistence using SQLAlchemy bulk insertions.

### 4.2 Synthetic Demo Service
- **Role**: Provides reliable, deterministic cybersecurity testbeds for demonstrations, automated tests, and benchmark evaluations.
- **Characteristics**:
  - Fixed seed initialization (`random_seed=42`) ensuring bit-for-bit repeatability across test runs.
  - Pre-seeded asset catalog: 50 Users (Admin, Privileged, Standard), 30 Devices (Workstations, Laptops, BYOD), 10 Servers (Tier-1 DB, Gateway, Tier-2 Apps).
  - 30 days of synthetic historical normal telemetry establishing stable UEBA baselines.
  - Deterministic injection engines for the 6 core scenarios:
    1. Baseline Normal Activity (routine authentications, periodic heartbeat transfers).
    2. Brute-Force to Compromise (5 failures, 1 success, new device, suspicious process, high egress).
    3. Impossible Travel (New York to Tokyo within 12 minutes, >10,000 km/h).
    4. Suspicious Execution (Unauthorized binary spawning under regular unprivileged user context).
    5. Lateral Movement (Initial workstation pivot -> SSH/RDP to Gateway -> Tier-1 privilege escalation).
    6. Exfiltration & Sensitive Data Transfer (High-volume anomalous egress to foreign public IP).

### 4.3 Detection & UEBA Engine
- **Role**: Dual-layer detection combining deterministic heuristics with statistical and unsupervised machine learning.
- **Layer 1: Deterministic Heuristic Engine**:
  - Sliding evaluation of threshold counters (e.g., 5 failed logins within 5 minutes).
  - Geospatial velocity calculation via Haversine formula for impossible travel.
  - Process novelty heuristics against baseline asset allow-lists.
- **Layer 2: Isolation Forest Anomaly Detection**:
  - Scikit-learn unsupervised anomaly detector trained on normal activity feature vectors.
  - Generates continuous anomaly score normalized from 0 to 100.
  - Computes feature contributions explaining why an event deviated from normal behavior.
- **Baseline Profiling**:
  - User and Device baseline objects storing active hours (bitmasks/intervals), authorized devices, typical source subnets, median data transfer volumes, and known process hashes.

### 4.4 Alert Deduplication & Correlation Service
- **Role**: Groups disparate detection signals into coherent, actionable security incidents to eliminate SOC alert fatigue.
- **Correlation Mechanism**:
  - Configurable 15-minute sliding time window.
  - Temporal and topological graph clustering: merges events that share common entities (`username`, `device_id`, `source_ip`, `destination_ip`) or causal parent-child process relationships.
  - Multi-stage state machine transitions an alert chain from `NEW` to `INVESTIGATING` to `CONTAINMENT_RECOMMENDED` based on kill-chain progression (e.g., Initial Access -> Execution -> Lateral Movement -> Exfiltration).

### 4.5 Risk Scoring Engine
- **Role**: Computes an objective, fully transparent, mathematically grounded risk score from 0 to 100 for each incident.
- **Formula**:
  $$\text{Risk Score} = \min\left(100, \sum_{i=1}^{6} w_i \cdot S_i\right)$$
  Where:
  - $w_1 = 0.25$ (Anomaly Score $S_{\text{anomaly}} \in [0, 100]$)
  - $w_2 = 0.20$ (Threat Severity Score $S_{\text{severity}} \in \{10, 25, 50, 75, 100\}$)
  - $w_3 = 0.15$ (Asset Criticality Score $S_{\text{asset}} \in \{40, 75, 100\}$)
  - $w_4 = 0.15$ (Identity Sensitivity Score $S_{\text{identity}} \in \{50, 75, 100\}$)
  - $w_5 = 0.15$ (Event Sequence Score $S_{\text{sequence}} = \min(100, \frac{\text{event\_count}}{10} \times 100)$)
  - $w_6 = 0.10$ (Attack Stage Score $S_{\text{stage}} \in \{30, 50, 70, 80, 100\}$)
- **Organizational Metric**: Computes the tenant-wide `Security Health Score` (labeled: `INTERNAL EVALUATION METRIC - NON-INDUSTRY STANDARD`).

### 4.6 MITRE ATT&CK Mapping Service
- **Role**: Maps incident evidence to the MITRE ATT&CK Enterprise Framework using an offline, structured JSON/PostgreSQL mapping catalog.
- **Evidence-Based Grounding**: Each technique assignment links directly to the specific `event_id`(s) that triggered the rule or ML detection.
- **Multi-Tactic Support**: Accounts for techniques that span multiple tactics (e.g., *Valid Accounts* (T1078) mapped across Initial Access, Persistence, Privilege Escalation, or Defense Evasion depending on evidence context).

### 4.7 Digital Twin & Response Simulation Service
- **Role**: Maintains an active in-memory topological model of the enterprise infrastructure to simulate containment and mitigation without touching real systems.
- **Data Model**: Directed graph ($G = (V, E)$) where vertices represent Users, Sessions, Devices, Servers, Services, and Data Assets; edges represent active connections, authorizations, and parent-child dependencies.
- **Blast Radius Analysis**:
  - Traverses the graph from the target isolation/block node.
  - Computes direct impacts: severed user sessions, terminated service ports.
  - Computes transitive impacts: downstream application outages, database disconnection, business process disruption.
  - Calculates estimated risk reduction vs. operational disruption cost.
- **Response Gate Modes**:
  - `OBSERVE`: Recommendations generated and logged; no simulated state mutation.
  - `RECOMMEND`: Every simulated action requires explicit human approval.
  - `CONTROLLED_AUTONOMOUS`: Low-impact reversible actions simulate automatically; high-impact actions (`SIMULATE_BLOCK_IP`, `SIMULATE_ISOLATE_DEVICE`) require Security Analyst or Security Admin approval.

### 4.8 AI Investigation Copilot Service
- **Role**: Synthesizes human-readable incident briefs, root-cause timelines, and response rationale strictly grounded in database evidence.
- **Contract Interface**: `LLMProviderInterface` provides an abstracted boundary allowing interchangeable backends (OpenAI, Anthropic, Ollama, HuggingFace, or Local Heuristic Engine).
- **Zero-Hallucination Fallback**:
  - When no external LLM is configured or available, a deterministic query engine constructs structured natural-language briefs directly from SQL entities.
  - If requested evidence is absent from the database, the service returns the exact required fallback:
    ```text
    I don't have enough evidence in the available security data.
    ```
- **Strict Privacy**: Event redaction rules are applied prior to feeding prompts to any external interface.

### 4.9 Tamper-Evident Audit Service
- **Role**: Cryptographically seals all analyst decisions, simulated responses, ingestion batches, and configuration modifications.
- **Data Structure**: Strict append-only hash chain where every record incorporates the SHA-256 hash of the preceding record:
  $$\text{Hash}_n = \text{SHA256}(\text{Hash}_{n-1} \parallel \text{Timestamp}_n \parallel \text{Actor}_n \parallel \text{Action}_n \parallel \text{CanonicalPayload}_n)$$
- **Concurrency & Fork Prevention**: Writes are guarded by database-level sequential table locking or anchor row updates (`SELECT ... FOR UPDATE`), guaranteeing a single linear sequence with zero forks.
- **Verification Utility**: Exposes an on-demand audit verification engine that traverses the ledger sequentially from the genesis block, flagging any corrupted or modified records.

### 4.10 Model Management & Continuous Learning Service
- **Role**: Collects analyst triage labels (`CONFIRMED_THREAT`, `FALSE_POSITIVE`, `NEEDS_REVIEW`) to evaluate and govern ML models without corrupting unsupervised models with unvalidated assumptions.
- **Capabilities**:
  - Evaluates Isolation Forest performance metrics (Precision, Recall, F1) against historical analyst ground-truth labels.
  - Compiles curated training corpora for supervised classification models.
  - Model Governance Gate: Retrained model artifacts are versioned, evaluated against validation datasets, and cannot be promoted to active production scoring without explicit Security Admin approval.

## 6. Verification and Acceptance Matrix

| Architecture Dimension | Verification Method | Success Criteria |
| :--- | :--- | :--- |
| **Operational Boundaries** | Static analysis & code audit | Zero system-level subprocess calls (`os.system`, `subprocess.Popen`) targeting system firewalls, interfaces, or users. |
| **Output Labelling** | Automated schema test | All API responses containing generated or simulated data carry the required taxonomy labels (`SYNTHETIC DATA`, `SIMULATED ACTION`, etc.). |
| **Audit Immutability** | Database concurrency test | Concurrent audit log writers produce an unbroken sequential SHA-256 chain verified by `GET /api/v1/audit/verify`. |
| **Deterministic Replay** | Seed comparison test | Running `generate-normal` or `generate-coordinated-attack` with `seed=42` produces bit-identical records across successive runs. |
| **Grounded AI Synthesis** | Boundary test | Queries requesting non-existent telemetry trigger the exact fallback string: *"I don't have enough evidence in the available security data."* |
